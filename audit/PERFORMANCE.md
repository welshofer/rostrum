# Performance and fidelity baseline — 2026-10-01

Machine: Apple M5, 32 GiB RAM, macOS 26.7, Apple Swift 6.4
(swiftlang-6.4.0.34.1), arm64. Release build; three samples per deck, medians
below. Benchmarks ran serially before the final full test gate. No sustained-load
or thermal characterization was performed. This is a current baseline, not a
before/after speedup claim.

| Fixture | Slides | PPTX MB | Open ms | Serialize ms | First SVG pass ms | Repeat SVG pass ms | Peak process MiB |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| small | 3 | 0.021 | 0.70 | 0.51 | 1.49 | 0.13 | 10.5 |
| large | 100 | 0.394 | 8.54 | 5.78 | 23.75 | 3.67 | 17.9 |
| images | 30 | 15.751 | 33.24 | 31.78 | 29.59 | 10.01 | 167.9 |

All slides render at 640 pixels wide. Timings exclude input/output disk I/O and
preservation checks. Peak RSS includes all retained SVGs plus independent ZIP
payload verification, so it must not be described as library-only peak memory.
The image-heavy case holds much more decoded image/SVG data than the text/chart
case. These workloads do not establish a library bottleneck worth changing an
algorithm for.

## Inputs and reproduction

- Small: `audit/snippet-output/review.pptx`, the three-slide README example.
- Large: `audit/benchmark-fixtures/large-100.pptx`, generated by
  `audit/benchmark-fixtures.swift`: 100 slides cycling text, section titles and charts.
- Images: `audit/sunflower-synthetic.pptx`, 30-slide Sunflower example from a clean
  checkout, with 13 procedural PNGs made by `audit/make-test-images.py`.

See [the runnable benchmark instructions](../Tools/rostrum-benchmark/README.md).
Raw per-sample JSON, resource-counter output, saved PPTX files and SVGs are in
[benchmarks](benchmarks/). Each process used three iterations and a fresh output
folder. A preliminary sandboxed run completed the small-deck fidelity checks but
could not read macOS resource counters; the recorded Release runs repeated all
three cases with counter access.

## Fidelity evidence

Every case passed exact decoded ZIP payload comparison, deterministic saves,
slide count preservation, repeated SVG equality, and SVG equality after reopening
the saved PPTX. These compare content before and after Rostrum, not its SVG
renderer against PowerPoint's rendering engine. Native acceptance is a separate
check; successful opening cannot prove matching typography, effects or cropping.

Lectern's app-hosted tests exercised real WebKit snapshots in 16:9, 4:3 and
portrait at widths 320 and 640. All four corner colors were sampled successfully
and output dimensions matched. Actual contact-sheet and filmstrip captures were
visually inspected at widths 720 and 1000:
[720px](preview-layout-720.png), [1000px](preview-layout-1000.png).
The failed-middle-slide contact sheet keeps badges 1, 2 and 3 and shows a failure
placeholder: [identity capture](preview-identity.png).

## Lectern timing limits

The small synthetic Debug SVGs took 56.94 ms, 2.27 ms and 8.56 ms for the first
bitmap request in each geometry case. The first case includes creation of the
shared WebKit host. The averages over 100 cached requests were 0.01046 ms,
0.01044 ms and 0.01161 ms respectively; raw data is
[preview-timings.json](preview-timings.json). Assertions and test-runner overhead
are included. This establishes cache behavior, not scrolling frame rate or
performance on image-heavy decks. Resolution participates in the cache key;
bitmap dimensions are bounded while preserving the slide ratio.

## Next measurements

Use a fixed foreign-authored deck corpus and the same machine to set regression
budgets. Measure time to first visible slide, full contact-sheet completion and
peak memory in a Release Lectern session with large images before making further
cache or concurrency changes. Preserve original parts and compare target-client
renders after every performance change. Paid model latency/content-quality
comparisons and live VoiceOver navigation were not measured in this pass.
